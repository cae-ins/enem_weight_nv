Architecture du Pipeline ENE-M — Données, Pondérations, Indicateurs

Version : 1.0 Date : 2026-03-16 Périmètre : Trimestre T4 2025 — extensible à tous les trimestres

1. Vue d’ensemble

Le dispositif ENE-M (Enquête Nationale sur l’Emploi — Volet Ménage) produit chaque trimestre des indicateurs officiels du marché du travail pour la Côte d’Ivoire. La production repose sur trois projets distincts qui forment une chaîne séquentielle : chaque projet consomme les outputs du précédent.

┌─────────────────────┐     ┌────────────────────────┐     ┌───────────────────────────┐
│  PROJET 1           │     │  PROJET 2              │     │  PROJET 3                 │
│  Apurement          │────▶│  Pondération           │────▶│  Tabulations / Bulletin   │
│  (Stata)            │     │  (R + Stata)           │     │  (R + Stata)              │
│                     │     │                        │     │                           │
│  données propres    │     │  données représent.    │     │  indicateurs officiels    │
└─────────────────────┘     └────────────────────────┘     └───────────────────────────┘

Le fil conducteur est membres.dta — la base individus qui traverse les trois projets en s’enrichissant à chaque étape :

Étape Ce que contient membres.dta
Après Projet 1 Variables collectées, nettoyées, codifiées (CIAP, CITP, branches)
Après Projet 2 + variable de pondération pmencor_ind (poids individuel calibré)
Dans Projet 3 Utilisée telle quelle pour calculer effectifs et taux pondérés

2. Rôle détaillé de chaque projet

2.1 Projet 1 — Apurement

Localisation : ENE-M-T4_2025/apurement/ Outil principal : Stata Inputs : exports .dta bruts de Survey Solutions (CAPI terrain) Outputs : bases .dta apurées par section + bases fusionnées codifiées

Ce que fait ce projet :

Survey Solutions exporte une base par module de questionnaire. Le projet découpe d’abord les bases brutes en sections thématiques (S0 à S15), puis apure chaque section indépendamment (contrôles de cohérence, corrections, gestion des valeurs manquantes), fusionne toutes les sections en une base ménage et une base individus, et enfin applique la codification métier : codes CIAP (activités), CITP (professions), branches d’activité (primaire / secondaire / tertiaire).

Pipeline interne (Stata) :

datain/brute/          (Survey Solutions exports)
     │
     ▼ standard_db.do
datain/standard/       (sections pré-découpées, 1 fichier par section)
     │
     ▼ apurement.do    (01-QM_S1 à 01-QM_S7, 01-INDIV_S1 à 01-INDIV_S15)
dataout/standard/
  ├── menage/          (QM_S0 à QM_S7 apurés)
  └── individu/        (INDIV_S1 à INDIV_S15 apurés)
     │
     ▼ Fusion.do
dataout/
  ├── menage/qx_eec_vf.dta        (base ménage finale)
  └── individu/membres.dta        (base individus fusionnée)
     │
     ▼ Codification_T4_2025.do
dataout/individu/membres.dta      (enrichi : CIAP + branches + CITP)

Fichiers de sortie utilisés en aval : - membres.dta → Projet 2 (base individus pour le calage) - qx_eec_vf.dta → Projet 3 (variables ménage pour les indicateurs)

2.2 Projet 2 — Pondération

Localisation : ENE_SURVEY_WEIGHTS/ Outil principal : R (package ReGenesees) Inputs : membres.dta (Projet 1) + données de dénombrement terrain (.xlsx) + RP 2021 Outputs : membres_menages_finale_T4.dta (membres.dta + pmencor_ind)

Ce que fait ce projet :

L’enquête ENE-M utilise un plan de sondage stratifié à deux degrés (ZD → ménage). Pour que les estimations soient représentatives de la population ivoirienne, chaque individu enquêté doit se voir attribuer un poids qui indique combien de personnes il représente dans la population réelle.

Ce projet calcule ces poids en trois étapes :

  1. Poids de base — inverse de la probabilité d’inclusion calculée à partir des données de dénombrement (comptage des ménages par ZD) et du plan de sondage (104 ZD pour Abidjan, 56 pour les autres régions).

  2. Correction pour la non-réponse — ajuste les poids pour compenser les ménages qui n’ont pas pu être interrogés.

  3. Calage (ReGenesees) — cale les poids finaux sur des totaux de population connus (RP 2021 projeté, par région × sexe × tranche d’âge) afin de garantir la cohérence avec les projections démographiques officielles. Plusieurs spécifications de calage sont testées (ex : 156X_1D, 312X_1D, 444X_1D) avec différentes combinaisons de contraintes.

Pipeline interne (R + Stata) :

data/01_raw/
  ├── Denombrement_update/{trimestre}/   (Excel dénombrements)
  └── RP_2021/                           (données recensement)
     │
     ▼ calc_base_weights_2.R
data/04_weights/                         (poids de base)
     │
     ▼ comp_followup_matrix.R            (correction non-réponse)
     │
     ▼ 01_Upload → 02_Prepare → 03_Pop → 04c_Calibration → 05_Attach
data/07_QUARTERLY_WEIGHTING/{annee}/{trimestre}/
  └── membres_menages_finale.dta         (base avec poids calibrés)
     │
     ▼ scripts/05_quality_control/       (Stata : contrôles qualité)
data/05_DERIVED_VARIABLES/{annee}/{trimestre}/
  └── membres_menages_finale_{trim}.dta  (version finale validée)

Variable clé produite : pmencor_ind (poids individuel corrigé et calé)

2.3 Projet 3 — Tabulations / Bulletin

Localisation : ENE_INDICATORS_TABULATIONS/ Outils : Stata (indicateurs + tableaux) + R (génération du bulletin Word/PDF) Inputs : membres_menages_finale_T4.dta (Projet 2) + qx_eec_vf.dta (Projet 1) Outputs : tableaux Excel d’indicateurs + bulletin trimestriel (Word/PDF)

Ce que fait ce projet :

À partir de la base pondérée, il calcule les indicateurs officiels du marché du travail selon les normes BIT/OIT : - Population en âge de travailler, taux d’activité - Emploi (ensemble, formel/informel, statut, branche, CITP) - Chômage (taux BIT) - Sous-utilisation de la main-d’œuvre (SU1, SU2, SU3) - Emploi inadéquat, temps partiel subi

Les calculs sont des sommes pondérées : - Effectif estimé = sum(pmencor_ind) sur la sous-population cible - Taux = sum(pmencor_ind | cible) / sum(pmencor_ind | référence) × 100

La base utilisée est multi-trimestrielle : les trimestres T2 2024 à T3 2025 sont empilés dans une seule base avec une variable trimestre, ce qui permet de produire des séries temporelles dans le bulletin.

Pipeline interne (Stata + R) :

Base/Base_brute/
  ├── membres.dta          (individus pondérés, depuis Projet 2)
  ├── poids.dta            (pondérations)
  └── qx_eec_vf.dta        (ménages, depuis Projet 1)
     │
     ▼ 1_1_Var_objectives_to_run.do   (création des variables analytiques)
     ▼ 1_2_Indicateur_Bulletin.do     (calcul des indicateurs pondérés)
     ▼ Tabulation_Bulletin_automatise.do  (export vers Excel par putexcel)
     │
Resultats_Tab/
  └── Tableaux_Indicateurs_ENEM.xlsx
     │
     ▼ workflow_complet.R → generer_bulletin.R
Publications/
  └── Bulletin_emploi_T4_2025.docx / .pdf

3. Architecture MinIO — Lac de données partagé

MinIO est le système de fichiers centralisé qui remplace les échanges manuels entre projets. Il joue le rôle de data lake avec une architecture médaillon à 4 couches.

3.1 Principe général

                  ┌──────────────────────────────────────────────────┐
                  │                   MinIO                          │
                  │                                                  │
   ┌──────────┐   │  ┌─────────┐  ┌─────────┐  ┌────────┐  ┌──────┐│
   │  Local   │◀──┼──│ staging │  │ bronze  │  │ silver │  │ gold ││
   │  (Stata) │──▶│  │         │  │         │  │        │  │      ││
   └──────────┘   │  └─────────┘  └─────────┘  └────────┘  └──────┘│
                  │                                                  │
   ┌──────────┐   │                                                  │
   │  Local   │◀──┼──────────────────────────────────────────────────┤
   │  (R)     │──▶│                                                  │
   └──────────┘   └──────────────────────────────────────────────────┘

Python (boto3) est l’unique interface avec MinIO — Stata et R ne communiquent jamais directement avec le stockage. Python télécharge les inputs avant chaque traitement et uploade les outputs après.

3.2 Définition des 4 couches

Couche Signification dans ce pipeline
staging Données brutes, immuables, déposées une seule fois. Inputs de chaque projet avant tout traitement.
bronze Données intermédiaires peu transformées. Utilisé ici pour les poids de base avant calage (ReGenesees).
silver Données traitées mais partielles. Bases apurées section par section, poids calibrés avant validation finale.
gold Outputs finaux validés, consommables directement par le projet suivant.

6. Interactions cross-projets via Gold

Le Gold est la zone de passage entre projets. Voici les deux transferts critiques :

Transfert 1 — Apurement → Pondération

Projet 1 écrit :   gold/enem/T4_2025/individu/membres.dta
                   gold/enem/T4_2025/menage/qx_eec_vf.dta

Projet 2 lit   :   gold/enem/T4_2025/individu/membres.dta
                   → téléchargé vers data/05_DERIVED_VARIABLES/2025/T4/

Ce transfert est critique : si membres.dta n’est pas dans Gold, le Projet 2 ne peut pas démarrer. L’orchestrateur du Projet 2 doit vérifier la présence du fichier avant de lancer R.

Projet 3 lit   :   gold/survey_weights/T4_2025/membres_menages_finale_T4_2025.dta

                   → téléchargé vers Bulletin_Trimestriel/Base/Base_brute/qx_eec_vf.dta

7. Orchestration globale (optionnelle)

Un orchestrateur global peut enchaîner les 3 projets en séquence avec vérification de chaque condition de succès :

# orchestrateur_global.py
# Lance les 3 pipelines en séquence avec contrôle de dépendance

Étape 1 : Apurement     → vérifie gold/enem/{trim}/individu/membres.dta
Étape 2 : Pondération   → vérifie gold/survey_weights/{trim}/membres_menages_finale.dta
Étape 3 : Tabulations   → vérifie gold/indicators/{trim}/Bulletin_emploi.docx

Mode reprises possibles :

python orchestrateur_global.py                  # pipeline complet
python orchestrateur_global.py --depuis 02      # reprend à la pondération
python orchestrateur_global.py --depuis 03      # reprend aux tabulations
python orchestrateur_global.py --dry-run        # affiche le plan
